# Нагрузка и отказоустойчивость

Отдельный контур проверок: свой compose, сценарии k6 и проигрывание настоящих
валидаций. Сервис здесь — тот же образ, что уходит жюри (корневой `Dockerfile`),
с лимитами из задания: 2 vCPU и 2 ГБ на копию.

Проверяем не только пропускную способность. Рабочее место диспетчера должно
оставаться живым и честным, когда что-то идёт не так: пропала связь с валидаторами,
упала копия сервиса, кто-то подбирает пароль, в выгрузке мусор.

## Запуск

Нужны Docker, [k6](https://k6.io) и `data/source/dataset.zip` (для приёма и провалов).

```sh
sh loadtest/run.sh build      # образ под архитектуру машины; PLATFORM=linux/amd64 — для жюри
sh loadtest/run.sh steps      # ступени 100 → 2000 запросов в секунду
sh loadtest/run.sh ingest     # приём test.csv целиком, пока экран под нагрузкой
sh loadtest/run.sh failover   # две копии за nginx, одна падает и возвращается
sh loadtest/run.sh auth       # перебор паролей: без защиты, с тысяч адресов, с одного
sh loadtest/run.sh gaps       # провалы данных: обрыв, дубли, опоздания, мусор
sh loadtest/run.sh glonass    # координаты 38 маршрутов: 600 и 6 000 отметок в секунду со сбоями
sh loadtest/run.sh stream     # поток валидаций ×1, ×10, ×100, ×1000 под нагрузкой экрана
sh loadtest/run.sh abuse      # злоупотребления: роли, огромные тела, медленные соединения
sh loadtest/run.sh stops      # посадки по остановкам: сумма, согласие с прогнозом, отказы
sh loadtest/run.sh all

# долгий прогон, 8 часов, своим контуром — остальное можно гонять параллельно
LOAD_PORT=18090 COMPOSE_PROJECT_NAME=tram-soak STATS_EVERY=10 sh loadtest/run.sh soak
```

Каждая проверка поднимает контур на порту 18080, снимает `docker stats` раз
в секунду и гасит контур за собой. Итоги — в `loadtest/results/<время>-<проверка>/`,
сводка — `report.md` там же.

| Файл | Что делает |
|---|---|
| `compose.yml` | профиль `single` — одна копия; `pair` — две копии за nginx |
| `nginx.conf` | балансировщик: упавшая копия выходит из ротации, оборванный запрос повторяется на соседней |
| `k6/common.js` | смесь запросов экрана: день маршрута по часам, месяц, риск-часы, пересчёт, выгрузка |
| `k6/steps.js` | ступени в открытой модели: запросы приходят с заданной частотой, как бы ни отвечал сервис |
| `k6/steady.js` | ровный фон экрана для приёма и отказа копии |
| `k6/flood.js` | перебор паролей: каждый запрос с новым неверным паролем |
| `replay.py` | проигрывание вторника 21 октября 2025 года с поломками потока |
| `glonass.py` | эмулятор навигационной платформы: вагоны 38 маршрутов на настоящих трассах, сбои терминалов |
| `stream.py` | непрерывный поток валидаций в реальном темпе или быстрее, отставание экрана от потока |
| `abuse.py` | злоупотребления: что шлём, какой ответ правильный, что пришло |
| `stops.py` | посадки по остановкам по всей сетке окна и отказы метода |
| `report.py` | таблицы из итогов k6 и `docker stats` |
| `k6/baseline.js` | прежний короткий замер: 50 пользователей, 30 секунд |

## Результаты

MacBook на Apple M4 Pro, Docker Desktop, образ linux/arm64 с лимитом 2 vCPU и 2 ГБ;
k6 работает на той же машине. Образ linux/amd64 проверен на работоспособность
под эмуляцией: задержки под эмуляцией не показательны, их не приводим.

### Пропускная способность экрана

| Запросов в секунду | Отвечено в секунду | Медиана, мс | p95, мс | p99, мс | Ошибок |
|---|---|---|---|---|---|
| 100 | 100 | 1,9 | 4,5 | 16 | 0 |
| 300 | 300 | 1,0 | 2,6 | 4,0 | 0 |
| 500 | 500 | 0,9 | 1,8 | 3,7 | 0 |
| 1 000 | 1 000 | 0,6 | 1,1 | 3,3 | 0 |
| 2 000 | 2 000 | 0,4 | 0,9 | 6,8 | 0 |
| 4 000 | 2 539 | 1 240 | 3 020 | 4 492 | 0,25 % |

Потолок одной копии — около 2 500 ответов в секунду: дальше процессор упирается
в лимит (189 % из 200 %), и очередь растёт. Требование задания — сотни запросов
в секунду при p95 до 300 мс — выполняется с запасом на порядок. Память — 250 МиБ
в рабочем режиме.

Для масштаба: 50 рабочих мест, которые обновляют экран раз в 30 секунд, — это
меньше двух запросов в секунду. Пропускная способность запросов сервису не угрожает,
поэтому основные проверки ниже — про отказы.

### Приём валидаций

`test.csv` целиком — 13 391 571 строка, 2,2 ГБ — отправлен одним потоком в `/api/ingest`,
пока экран работал с нагрузкой 300 запросов в секунду.

| Величина | Значение |
|---|---|
| Время приёма | 13,3 с |
| Скорость | ≈ 1 000 000 строк в секунду |
| Посадок / не посадок / битых | 12 754 520 / 637 051 / 0 |
| Экран в это время: медиана / p95 / p99 | 1,2 / 3,0 / 9,4 мс |
| Память, пик | 502 МиБ |

Разбор выгрузки занимает одно ядро из двух, второе остаётся экрану. Для сравнения:
десять маршрутов в пиковый час дают около семи валидаций в секунду, вся трамвайная
сеть Москвы — порядка десятков в секунду. Запас приёма — четыре порядка.

### Отказ копии

Две копии за nginx, ровная нагрузка 300 запросов в секунду 90 секунд. На 30-й секунде
копия `api-a` гасится `kill`, на 60-й возвращается.

| Величина | Значение |
|---|---|
| Запросов | 27 001 |
| Ошибок | 0 |
| Медиана / p95 / p99 | 1,2 / 2,5 / 5,3 мс |

Запрос, оборвавшийся на упавшей копии, nginx повторяет на соседней, поэтому
диспетчер падения не видит. Упавшую копию nginx пробует снова через 5 секунд,
так что вернувшаяся встаёт в ротацию сама.

### Перебор паролей

Диспетчеры — 200 запросов в секунду с хоста; атака — 100 запросов в секунду с новым
неверным паролем каждый раз, из отдельного контейнера. Минута на случай.

| Случай | Диспетчеры: медиана / p95 | Ошибок у диспетчеров | Проверено bcrypt | Отбито 429 |
|---|---|---|---|---|
| Без защиты | 16,6 с / 60 с | 9,8 % | 216 | 0 |
| Атака с тысяч адресов: лимит bcrypt | 1,0 / 37 мс | 0 | 486 | 5 515 |
| Атака с одного адреса: блокировка | 1,2 / 3,4 мс | 0 | 22 | 5 979 |

Проверка пароля через bcrypt стоит около 55 мс процессора, а неверные пароли
не кэшируются. Без защиты сотни неверных паролей в секунду занимают оба ядра,
и экран диспетчера перестаёт отвечать: это отказ в обслуживании без единого
верного пароля. Защита — в `api/…/LoginGuard.java`:

- адрес с более чем 20 неверными паролями за минуту получает 429 на 5 минут;
- только что не подошедшая пара отклоняется без повторного bcrypt;
- новых проверок bcrypt — не больше 8 в секунду на весь сервис (около половины ядра);
  уже проверенные пары идут мимо лимита, поэтому работающий диспетчер атаки не замечает;
- одновременные первые запросы с одной парой ждут одну проверку, а не каждый свою:
  в начале смены экран открывают разом.

Пороги задаются переменными `GUARD_FAILS_PER_IP`, `GUARD_BLOCK_MINUTES`,
`GUARD_BCRYPT_PER_SECOND`. За балансировщиком адрес клиента берётся
из `X-Forwarded-For` (`FORWARD_HEADERS=framework`), и балансировщик этот заголовок
перезаписывает, а не дописывает: иначе клиент подставил бы чужой адрес.

### Провалы данных

Вторник 21 октября 2025 года из `test.csv` переносится на дни окна прогноза
и отправляется в `/api/ingest` почасовыми пачками. Пересчёт остатка дня по принятому
факту (`/api/nowcast` без `fact`, `until=12`) сравнивается с эталоном — тем же
пересчётом по чистому факту, переданному прямо в запросе.

| Поломка | Что получилось |
|---|---|
| Поток без сбоев | множитель совпал с эталоном на всех маршрутах |
| Каждая пачка пришла дважды | повторы по `X-Batch-Id` отклонены, множитель совпал |
| Маршрут 7: нет связи с валидаторами в 8 и 9 часов | часы найдены как провал и не вошли в отношение: 1,025 против эталона 0,995; если считать их нулём, было бы 0,894 |
| Час 9 пришёл после часа 11 | до его прихода час 9 помечен провалом; после — множитель совпал |
| Тишина с 7 часов, потом часы 7—11 одной пачкой | 89 676 строк за 0,07 с, множитель совпал |
| Маршрут 17 молчит весь день | пересчёт не применён, остаток дня — обычный прогноз |
| Маршрут 26: посадки 8 часов удесятерены | множитель остановился на пределе 1,118 |
| В пачках тысяча битых строк | все отклонены с номером строки и причиной, ответ 200, факт не тронут |

Провалом считается час, где факт меньше пятой части прогноза: так выглядит обрыв
связи с валидаторами, а не пустой трамвай. Без этого правила один такой час уводил
весь остаток дня к нижней границе 0,8.

### Координаты ГЛОНАСС

Эмулятор ведёт вагоны всех 38 трамвайных маршрутов Москвы по настоящим трассам:
десять маршрутов задания и 28 остальных из OSM, по 16 вагонов — 608 вагонов.
У маршрутов задания бортовые номера настоящие, из валидаций. В поток подмешаны
сбои терминалов, каждый двадцатый вагон через 10 секунд замолкает. Экран в это время —
300 запросов в секунду; порог «нет связи» на время проверки — 30 секунд.

| Отметка вагона | Отметок в секунду | Пачка 608 отметок: медиана / p95 | Вагонов на связи / без связи |
|---|---|---|---|
| раз в секунду | 601 | 3,1 / 7,3 мс | 578 / 30 из 30 ожидаемых |
| десять раз в секунду | 5 924 | 2,7 / 5,1 мс | 578 / 30 из 30 ожидаемых |

Экран за четыре минуты — 45 тысяч запросов, p95 2,6 мс, ошибок нет.

| Сбой терминала | Подмешано, 1 Гц | Отброшено | Подмешано, 10 Гц | Отброшено |
|---|---|---|---|---|
| Нули вместо координат | 60 | 60 | 799 | 799 |
| Скачок на 3 км | 171 | 171 | 1 752 | 2 351 |
| Время из будущего | 37 | 37 | 384 | 384 |
| Повтор отметки | 333 | 333 | 3 348 | 3 343 |
| Опоздавшая отметка | 177 | 177 | 1 781 | 1 782 |

На 1 Гц сверка сошлась до отметки. На 10 Гц лишние 599 скачков — первая отметка
вагонов второго прогона: те же бортовые номера появились в новых местах трассы.
Сервис отбросил её как скачок и со второй согласной отметки перепривязал вагон —
все 578 на связи. Пять повторов на стыке прогонов засчитаны как опоздавшие.

Вся трамвайная сеть Москвы — порядка тысячи вагонов; при отметке раз в секунду это
около тысячи отметок в секунду. Приём 5 924 отметок в секунду вместе с экраном занял
в среднем 0,3 ядра, в пике 0,9 из двух.

### Поток валидаций в реальном темпе

Тот же вторник идёт в `/api/ingest` пачками, как слал бы приёмник от валидаторов;
после каждой пачки сервис спрашивается, какая последняя валидация маршрута 25 уже видна.
Экран в это время — 300 запросов в секунду.

| Темп | Минут суток прошло | Строк | Строк в секунду | Пачка: медиана / p95 | Отставание экрана: медиана / p95 |
|---|---|---|---|---|---|
| ×1, пачка раз в 5 с | 1 | 381 | 6 | 3,7 / 91 мс | 35 / 60 с |
| ×10 | 10 | 2 124 | 35 | 4,0 / 33 мс | 4 / 9 с |
| ×100 | 150 | 38 372 | 426 | 9,2 / 48 мс | 0,4 / 1,6 с |
| ×1000, пачка раз в 1 с | 1 133 | 256 207 | 3 713 | 7,6 / 14 мс | 0 / 0,7 с |

Экран — 99 тысяч запросов, p95 2,2 мс, ошибок нет. Отставание при ×1 — не задержка
сервиса: время последней валидации отдаётся с точностью до минуты, и отставание меньше
минуты при ×1 не различить. При ×100 и ×1000 видно настоящее: меньше двух секунд
от пачки до экрана. ×1000 — это сутки десяти маршрутов за полторы минуты,
вдесятеро больше пикового потока всей трамвайной сети.

### Злоупотребления

Проверки идут из отдельного контейнера — у атаки свой адрес; экран в это время —
100 запросов в секунду, ошибок нет, p95 3,6 мс.

| Проверка | Ответ |
|---|---|
| Запрос без пароля | 401 |
| Диспетчер шлёт валидации или координаты | 403 |
| Сервис приёма читает прогноз | 403 |
| JSON на 10 МБ в пересчёт | 413 за 0,04 с |
| Факт на 10 000 пар в адресе | 414 |
| Заголовки на 40 КБ | 431 |
| 500 несуществующих маршрутов | 404 |
| Маршрут 7, повторённый 500 раз | 200, 86 КБ — как на один маршрут |
| Строка на 5 МБ или 4 МБ двоичного мусора в приём | 400 за 0,04 с |
| 25 000 выдуманных бортов | в памяти 20 000, остальные — `overflow` |
| 2 000 медленных соединений | запрос диспетчера — 8 мс; через 60 с сервис закрыл все |
| Перебор, потом верный пароль с чужим `X-Forwarded-For` | 429: адрес заблокирован, заголовку без балансировщика не верим |

Три дыры нашлись этой проверкой и закрыты: повтор маршрута в списке раздувал ответ
до 43 МБ, а слишком длинное тело или строка обрывали соединение ошибкой 500 вместо
понятного отказа. Оговорка: блокировка перебора — по адресу, и диспетчеры за одним
NAT с атакующим тоже получат 429 на пять минут; это видно, если запустить атаку
с того же адреса, что и экран.

### Посадки по остановкам

`/api/stops` раскладывает прогноз маршрута за час по остановкам долями из октябрьских
валидаций; доли есть у маршрутов 7, 17, 25, 28 и 50. Проверка обходит всю сетку окна —
5 маршрутов × 61 день × 24 часа и суммы за день, 7 625 срезов.

| Проверка | Результат |
|---|---|
| Сумма по остановкам вместе с `unallocated` равна `routeTotal` | во всех 7 625 срезах, без допуска |
| `routeTotal` равен прогнозу маршрута из `/api/forecast` за тот же час или день | во всех срезах |
| Пустой список остановок при ненулевом маршруте | ни одного |
| Время ответа | медиана 0,6 мс, p95 1,6 мс |
| Маршруты 1, 5, 11, 12, 26 без долей и маршрут вне прогноза | 404 |
| Час 25, дата вне окна / без пароля / роль приёма | 400 / 401 / 403 |
| Сервис без файлов долей | стартует, прогноз отвечает, `/api/stops` — 404 |

Первый прогон нашёл срез, где посадки терялись: маршрут 50, суббота 8 ноября, 3 часа ночи.
Прогноз маршрута — 4 посадки, а в октябрьские выходные в этот час валидаций не было, и
список остановок приходил пустым. Теперь час без долей берёт доли ближайшего часа того же
типа дня, а остаток округления раздаётся по остановкам, так что сумма сходится точно.
В смеси ступеней нагрузки `/api/stops` — десятая часть запросов; от 100 до 2 000 запросов
в секунду ошибок нет, p95 не выше 3,3 мс.

### Долгий прогон

Восемь часов одновременно: экран — 50 запросов в секунду, 608 вагонов с отметкой
раз в секунду и сбоями, поток валидаций в реальном темпе. k6 — кусками по полчаса,
чтобы видеть, не растут ли задержка и память к концу.

Результат — после окончания прогона.
